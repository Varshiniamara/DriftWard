Statistical Corroboration & Streaming Checks

Kolmogorov-Smirnov (KS) Validation:
To eliminate false alarms caused by temporary mechanical spikes, PSI triggers must be validated by a two-sample Kolmogorov-Smirnov test. The KS test calculates the supremum distance $D$ between the cumulative empirical distributions of the live and reference windows.

For Air Temperature: $D_{KS} = 0.412$ | Significance $p$-value: $0.003$. Reject null hypothesis of identical distributions with >99% confidence.

ADWIN (Adaptive Windowing) Error Tracking:
For fast-changing streams, ADWIN monitors model prediction errors. It compares averages between dynamically adjusted sub-windows ($W_0$ and $W_1$). When their difference exceeds a mathematically defined threshold, older historical data is pruned, and a concept drift alarm triggers.

  • Older Sub-Window ($W_0$): Mean Error Rate $\mu_{err} = 3.1\%$
  • Recent Sub-Window ($W_1$): Mean Error Rate $\mu_{err} = 8.4\%$
  • Status: Real-time drift confirmed; data window boundary reset.

Intelligent Decision & Governance Engine
Upon drift confirmation, the system runs a structured, multi-tier analysis to isolate root causes and select the safest, most resource-efficient recovery path—protecting against infinite retraining loops and model regression.
LLM Root-Cause Reasoning Layer

The coordinator routes the statistical drift payload to a local LLM analytical engine. The prompt includes exact feature-level PSI profiles, direction of distribution shifts, training provenance metadata, historical audit logs, and operational override rules. The engine evaluates this data to isolate the root cause, categorizing it into one of four key groups:

  • Environmental Variations: Natural seasonal temperature transitions or geographical environmental changes.
  • Process Changes: Intentional updates to operational parameters or raw material specifications.
  • Equipment Degradation: Progressive physical wear, such as component aging or sensor degradation.
  • Data Pipeline Faults: Communication loss, corrupted upstream ETL schemas, or hardware failures.

For seasonal temp shifts, the engine flags Environmental Variation with 91% confidence, selecting a full retraining strategy on a targeted data window.

Hard Governance Checkpoints

DriftWarden enforces three distinct governance checkpoints before modifying any operational model weights:

G1: Confidence Gating

The reasoning engine must classify the root cause with a confidence score of $\ge 0.75$ (scale 0.0 to 1.0) before executing recovery. If confidence falls below $0.75$, the strategy defaults to Monitor-Only and alerts site reliability engineering.

G2: Retraining Loop Prevention

Autonomous retraining runs are capped at a maximum of three within a rolling 24-hour window per asset. This protects against data poisoning and prevents continuous, wasteful resource usage.

G3: Hot Standby Rollback

Prior production model weights are marked immutable in the registry. The deployment orchestrator keeps a hot standby version, allowing full rollback execution in under 30 seconds.

Autonomous Recovery & Model Governance Pipeline
Once a recovery path is selected, the system manages a controlled training pipeline. No model version is promoted to production without passing strict validation checks, and all actions are recorded in an immutable audit registry.
Retraining and F1-Score Validation Gate

The framework manages retraining through three strict execution stages:

  1. Data Acquisition: Queries the feature store for the target data window (e.g., the last 30 days of production telemetry), normalizes inputs, and creates an 80/20 train/validation split.
  2. Model Execution: Spawns an ephemeral training instance. It runs standard fine-tuning or full retraining based on the decision engine's output.
  3. The F1-Score Validation Gate: Evaluates the candidate model on a held-out verification set, comparing its performance directly against the active production model:

$\text{F1}_{\text{candidate}} \ge \text{F1}_{\text{production}} + 0.01$

If the candidate model achieves an F1-score improvement of at least 0.01 (1%) and satisfies the absolute SLA baseline (e.g., F1 $\ge 0.90$), the deployment gate passes. Otherwise, the candidate is rejected, and the existing model is retained.
